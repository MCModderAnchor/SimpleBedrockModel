# SBM 世界粒子性能测量

实测基于 Forge 1.20.1 的开发客户端，覆盖限帧与无上限基线、烟雾 tick、GPU 原型和 CPU 热点。各轮使用 1280×720、关闭 VSync 的独立超平坦场景。原始 CSV、截图和 JFR 的链接指向本地 `build/` 输出。场景、测量口径和复测命令见 [试验方案](experiments.md)。

## 12,000 粒子基线开销分布

下表统一看 12,000 个存活世界粒子。耗时是三轮 P50 的中位数。括号内的 CPU 占比用三个阶段在全部采样帧和 tick 中的累计耗时计算，因此已计入渲染帧率和 20 Hz 粒子更新频率的差异。GPU 列是覆盖批次上传与绘制的异步查询，可能含 GPU 等待 CPU 提交的时间。

| 场景 | CPU 四角展开和写入（ms/帧） | CPU 批次提交（ms/帧） | 粒子更新（ms/tick） | GPU 批次查询（ms/帧） |
| --- | ---: | ---: | ---: | ---: |
| 120 FPS 上限，小粒子，逐顶点写入 | 2.741（90.7%） | 0.084（2.8%） | 1.121（6.5%） | 0.261 |
| 120 FPS 上限，小粒子，Embeddium | 0.917（76.0%） | 0.083（7.2%） | 1.205（16.8%） | 0.118 |
| 无上限，小粒子，逐顶点写入 | 2.653（94.1%） | 0.067（2.5%） | 1.101（3.4%） | 0.103 |
| 无上限，小粒子，Embeddium | 0.771（90.0%） | 0.053（6.7%） | 1.121（3.4%） | 0.110 |
| 无上限，基础大粒子，Embeddium | 0.740（89.4%） | 0.057（7.1%） | 1.156（3.5%） | 0.135 |
| 无上限，`test_basic_smoke`，Embeddium | 0.750（86.5%） | 0.059（6.9%） | 2.122（6.5%） | 0.133 |

Embeddium 小粒子组的基础更新累计耗时，按渲染帧摊分后为限帧时 0.206 ms/帧、解除上限后 0.029 ms/帧。固定存活数量下的粒子更新约为 1.1–1.2 ms/tick。

## 120 FPS 上限基线

在 Forge 1.20.1 开发客户端的独立超平坦世界中，使用现有 `ParticleEngine`、`SnowStormParticle` 和 SBM 粒子材质批次。固定相机、烟雾纹理第一格、`PARTICLES_ALPHA`、`ROTATE_XYZ` 和粒子位置。大粒子组把相同布局中每个 billboard 的边长放大十倍。测试使用 i9-13900HX、RTX 4060 Laptop GPU（驱动 591.74）、Embeddium 0.3.31、1280×720，帧率上限 120，关闭 VSync，测试客户端未加载 Oculus。

两条路径在同一客户端内切换 SBM 的写入分支。`VertexConsumer` 保留逐顶点写入，Embeddium 启用 `SodiumParticleVertexWriter`。每组预热 120 帧、采 240 帧，完成三轮，共 24 组、5,760 个帧样本和 966 个 tick 样本。第二轮反转两条路径的顺序。下表给出各轮 P50 再取中位数，斜线两侧依次是 `VertexConsumer` 和 Embeddium，单位为毫秒。

| 场景 | CPU 四角展开和写入 / 帧 | CPU 批次提交 / 帧 | GPU 查询 / 帧 | 粒子 tick |
| --- | ---: | ---: | ---: | ---: |
| 1,024 小粒子 | 0.241 / 0.083 | 0.017 / 0.018 | 0.089 / 0.017 | 0.106 / 0.106 |
| 4,096 小粒子 | 0.951 / 0.292 | 0.035 / 0.034 | 0.019 / 0.100 | 0.355 / 0.387 |
| 12,000 小粒子 | 2.741 / 0.917 | 0.084 / 0.083 | 0.261 / 0.118 | 1.121 / 1.205 |
| 12,000 大粒子 | 2.760 / 0.882 | 0.092 / 0.084 | 0.194 / 0.131 | 0.979 / 1.072 |

12,000 个小粒子时，Embeddium 将 CPU 展开和写入从 2.741 降至 0.917 ms/帧，P95 从 3.714 降至 1.458 ms/帧。两条路径的批次提交均约 0.08 ms/帧。GPU `GL_TIME_ELAPSED` 包住现有批次的上传与绘制，可包含 CPU 提交期间的 GPU 空闲。Embeddium 下 12,000 个小粒子的三轮 GPU P50 为 0.103–0.245 ms，大粒子为 0.127–0.191 ms，区间重叠，本轮难以量出覆盖率的独立影响。粒子 tick 包括现有 Molang 变量绑定和生命周期更新。测试场景使用静止的固定粒子，真实效果的生成、碰撞、环境光和事件成本留待单独验证。

## 解除帧率上限后的复测

在相同的 1280×720 场景解除帧率上限，VSync 保持关闭。为保持每组的 tick 样本量，预热至少 120 帧且满 1 秒，采样至少 240 帧且满 2 秒。三轮共 24 组、47,874 个帧样本和 972 个 tick 样本。平均 FPS 由连续两帧渲染结束之间的间隔计算，下表取三轮的中位数。CPU 和 GPU 仍取各轮 P50 的中位数，斜线两侧依次是 `VertexConsumer` 和 Embeddium。

| 场景 | 平均 FPS | CPU 四角展开和写入（ms/帧） | GPU 查询（ms/帧） |
| --- | ---: | ---: | ---: |
| 1,024 小粒子 | 1,520 / 2,157 | 0.218 / 0.062 | 0.010 / 0.008 |
| 4,096 小粒子 | 729 / 1,458 | 0.879 / 0.254 | 0.020 / 0.017 |
| 12,000 小粒子 | 295 / 770 | 2.653 / 0.771 | 0.103 / 0.110 |
| 12,000 大粒子 | 294 / 736 | 2.649 / 0.768 | 0.179 / 0.145 |

在 12,000 个小粒子场景中，Embeddium 的 CPU 展开和写入 P50 从 120 FPS 上限下的 0.917 ms/帧降至 0.771 ms/帧，P95 从 1.458 降至 0.912 ms/帧。逐顶点写入在解除上限后仍花 2.653 ms/帧。Embeddium 的批次提交为 0.053 ms/帧，两个尺寸下的粒子 tick P50 都约为 1.1 ms/tick。

Embeddium 下，大粒子的 GPU 查询 P50 从 0.110 增至 0.145 ms/帧，平均 FPS 从 770 降至 736。三轮 GPU P50 的区间分别为小粒子 0.103–0.119 ms、大粒子 0.134–0.166 ms，解除上限后覆盖率的影响更容易辨认。GPU 查询的区间仍包含批次上传、draw 和可能的提交空闲。 [无上限统计汇总及逐轮数据](../../build/world-particle-benchmark/run-02507cc62b2e4d61a9f10f726bd95f37/particle-results-14322401962773291903/summary.txt)

## 带 Molang 的烟雾粒子 tick

沿用 1280×720、Embeddium 和无 FPS 上限设置，测量 `example:test_basic_smoke` 的粒子 tick。烟雾保留原有运行时组件，每 tick 更新翻页 UV、运动和渐变颜色，渐变进度由 `v.particle_age / v.particle_lifetime` 求值。为了让每组的存活粒子数固定，测试在采样前统一生成粒子，将寿命设成 10 秒并错开初始年龄。采样覆盖稳定存活期，发射器调度、生成和死亡开销需另测。 [粒子定义](../../src/main/resources/assets/example/particle_definitions/test_basic_smoke.particle.json)

三轮共 27 组、77,397 帧和 1,090 个 tick 样本。基础组执行变量绑定和基础粒子更新。粒子 CPU 占比使用采样窗口内的 tick 总耗时除以 tick、CPU 展开与顶点写入、CPU 批次提交三项的耗时之和。客户端 tick 占比用同一批样本的客户端 tick 总耗时作分母。以下耗时为各轮 P50 的中位数，占比为三轮各自比例的中位数。

| 存活粒子数 | 基础 tick（ms） | 烟雾 tick（ms） | 烟雾 tick 占客户端 tick | 烟雾 tick 占粒子 CPU | 烟雾 tick 占测量时长 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1,024 | 0.100 | 0.178 | 21.0% | 2.3% | 0.37% |
| 4,096 | 0.438 | 0.689 | 50.3% | 3.7% | 1.44% |
| 12,000 | 1.156 | 2.122 | 75.4% | 6.6% | 4.33% |

12,000 个烟雾粒子的 tick P95 为 2.385 ms。相比基础组，三轮配对的 P50 分别增加 0.856、0.966 和 1.029 ms/tick，覆盖烟雾的翻页、运动和颜色更新。把渐变进度表达式替换成读取同一组绑定变量的等价 Java 除法，12,000 粒子组的 tick P50 为 2.141 ms。原定义减去 Java 对照的三轮差值为 −0.113、−0.019 和 +0.061 ms/tick，这次复测难以分离这一条 Molang 表达式相对 Java 的独立开销。

## 实例化和 AR compute 原型

首轮对照 Embeddium、实例化和 AR compute。各路径使用相同的固定 UV 和粒子批次。

三轮共 36 组、105,390 帧和 1,452 个 tick 样本。每组预热至少 1 秒、采样至少 2 秒，每轮轮换路径顺序。下表每格依次为粒子 CPU 准备加提交的 P50（ms/帧）、GPU 批次查询 P50（ms/帧）和平均 FPS。三项分别取三轮的中位数。

| 场景 | Embeddium | 实例化 | AR compute |
| --- | ---: | ---: | ---: |
| 1,024 小粒子 | 0.072 / 0.007 / 2,091 | 0.029 / 0.006 / 2,347 | 0.066 / 0.011 / 2,108 |
| 4,096 小粒子 | 0.275 / 0.015 / 1,436 | 0.096 / 0.011 / 1,967 | 0.228 / 0.030 / 1,526 |
| 12,000 小粒子 | 0.809 / 0.099 / 783 | 0.273 / 0.024 / 1,358 | 0.657 / 0.137 / 862 |
| 12,000 大粒子 | 0.826 / 0.124 / 748 | 0.273 / 0.052 / 1,392 | 0.662 / 0.162 / 881 |

12,000 个小粒子时，实例化减少了约 66% 的粒子渲染 CPU 耗时，AR compute 减少约 19%。三条路径的 CPU 准备 P50 依次为 0.753、0.240 和 0.578 ms/帧，CPU 提交为 0.056、0.030 和 0.073 ms/帧。AR 复用内核省下了 CPU 四角展开和四次顶点写入，保留了矩阵计算和打包，同时把 GPU 批次查询从 0.099 拉到 0.137 ms/帧。

## 24,000–96,000 粒子单批压力测试

Forge 1.20.1 的 `ParticleEngine` 默认每个 RenderType 最多保留 16,384 个粒子。这次仅在隔离客户端给基准专用 RenderType 注册容量 96,000 的队列，保留原 `ParticleEngine` 的 tick、可见性检查和渲染顺序。基准逐帧核对实际经过渲染的粒子数量。场景沿用前一轮的相机、纹理、绘制尺寸和混合状态，每条路径保持单批一次 draw。96,000 粒子额外测大 billboard，观察屏幕覆盖率的影响。

三轮共 48 组、31,736 帧和 1,989 个 tick 样本。每格依次为 CPU 准备加提交 P50（ms/帧）、GPU 批次查询 P50（ms/帧）和整帧平均 FPS，分别取三轮中位数。

| 场景 | Embeddium | 实例化 | AR compute | 自写 compute |
| --- | ---: | ---: | ---: | ---: |
| 24,000 小粒子 | 1.590 / 0.257 / 433 | 0.528 / 0.100 / 903 | 1.284 / 0.342 / 510 | 0.563 / 0.150 / 922 |
| 48,000 小粒子 | 3.260 / 0.614 / 221 | 1.430 / 0.284 / 402 | 2.717 / 0.790 / 246 | 1.567 / 0.425 / 426 |
| 96,000 小粒子 | 6.668 / 1.368 / 104 | 3.542 / 0.652 / 189 | 6.412 / 1.802 / 113 | 3.460 / 1.014 / 185 |
| 96,000 大粒子 | 6.756 / 1.517 / 100 | 3.412 / 0.903 / 181 | 6.278 / 1.880 / 109 | 3.249 / 1.054 / 206 |

96,000 个小粒子时，实例化和自写 compute 都将粒子渲染 CPU 耗时降到约 3.5 ms/帧，接近 Embeddium 的一半。实例化的 GPU 批次耗时在所有规模、所有轮次都低于自写 compute。整帧 FPS 的差异会随轮次反转，例如 96,000 大粒子组的自写 compute 为 162–238 FPS，实例化为 169–196 FPS。AR 的 CPU 相对收益随规模缩小，96,000 小粒子时 CPU 合计与基线只差 0.26 ms/帧，GPU 批次多 0.43 ms/帧。

96,000 粒子的基础 tick P50 为 7.8–8.9 ms，P95 为 10.5–11.2 ms。对各轮累计耗时取中位数，tick 占客户端 tick 的 92–93%，占整个窗口粒子 CPU 耗时的 19–21%。例如自写 compute 的小粒子组按渲染帧摊分，tick 和渲染分别平均花 0.984 和 3.764 ms/帧。两种尺寸的稳定截图在四条路径间逐像素一致。该容量依赖开发基准中的单队列设置，发布版仍受原粒子队列容量约束。 [统计汇总、逐轮 CSV 和截图](../../build/world-particle-benchmark/run-b59d79add8814e8fa567e29bc956110d/particle-results-9999427274745542633)

## 大批次 CPU 调用栈采样

在 24,000 和 96,000 个小粒子的无上限场景中，使用本机 IntelliJ IDEA 2024.2.0.1 自带的 Windows async-profiler，按 `event=cpu,interval=2ms` 录制。四条路径各采三轮，每组取约 5 秒的正式窗口。基准写出各组的 UTC 边界，分析只选取这些窗口内渲染线程的 `jdk.ExecutionSample`。粒子渲染样本按调用栈区分引擎遍历、粒子数据准备、打包和提交，粒子 tick 使用单独的样本计数。阶段占比来自采样次数，毫秒数据来自同轮基准的段计时。

共 24 组、39,889 帧和 41,982 个渲染线程 CPU 样本。其中 24,699 个样本可归入粒子渲染阶段。下表的 CPU 耗时为准备和提交之和的 P50，再取三轮中位数。右侧比例基于 96,000 粒子中能归因到该粒子渲染的 CPU 样本。

| 路径 | 24,000 CPU（ms/帧） | 96,000 CPU（ms/帧） | 视锥检查 | 引擎循环与分发 | 粒子状态 | 展开或记录写入 | 提交 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Embeddium | 2.066 | 8.913 | 16.5% | 12.7% | 1.9% | 42.5% 四角准备，14.7% 顶点写入 | 11.8% |
| 实例化 | 0.679 | 4.174 | 33.2% | 28.4% | 15.3% | 14.5% 紧凑记录 | 8.7% |
| AR compute | 1.666 | 6.917 | 22.3% | 14.1% | 11.2% | 33.5% 矩阵及记录写入 | 18.9% |
| 自写 compute | 0.792 | 3.655 | 35.4% | 24.7% | 15.9% | 13.8% 紧凑记录 | 10.2% |

实例化和自写 compute 在 96,000 个粒子时，有 60–62% 的渲染样本落在引擎循环、分发和视锥检查。视锥检查的热点包含 `FrustumIntersection.testAab`、`Frustum.cubeInFrustum` 和从 `Frustum.isVisible` 调用的 `AABB.equals`。较小的逐粒子成本包括 `ParticleGpuPrototype.push` 里的颜色和相机相对坐标准备，以及 `Compact.pack` 里的 `Buffer.nextPutIndex` 和直接缓冲区写入。比较 24,000 和 96,000 两组，每渲染千帧的紧凑记录写入样本分别增长约 4.0 倍和 3.7 倍，视锥检查增长约 4.0 倍和 4.4 倍。引擎循环与分发剩余样本增长更快，分别约 12.8 倍和 6.6 倍。这个剩余项基于栈归因，当前数据无法确认是哪条指令或哪一级缓存造成了增量。

Embeddium 的四角准备主要落在 `Quaternionf.transform` 和 `cosFromSinInternal`。顶点写入栈中有 `BufferBuilder.ensureCapacity` 检查。96,000 组还有 596 个 Embeddium 和 877 个 AR 样本只保留了原生三角函数及 `.unknown_Java`。表中未给这些样本指定调用方。采样轮的计时也高于先前的大批次运行，例如 96,000 Embeddium 从 6.668 升到 8.913 ms/帧，因此前一轮仍用作无 profiler 的性能基线。

## CPU 热点隔离实验（2026-11-24）

测量 24,000 和 96,000 个全部可见的小粒子。对照使用同一个实例化 shader、48 B 输入布局和粒子 tick。

三轮共 30 组、34,611 帧和 1,207 个 tick 样本。下表为各轮 P50 的中位数，CPU 准备区间含粒子遍历、视锥检查和打包，从批次 `begin` 后到 `end` 开始。首轮 96,000 粒子的四种改法均与基线逐像素一致。

| 对照 | 24,000 CPU 准备（ms/帧） | 96,000 CPU 准备（ms/帧） | 96,000 CPU 准备＋提交（ms/帧） |
| --- | ---: | ---: | ---: |
| 实例化基线 | 0.558 | 3.203 | 3.504 |
| 关闭逐粒子视锥检查 | 0.423 | 2.716 | 3.036 |
| 按固定地址写记录 | 0.459 | 2.921 | 3.228 |
| 关闭视锥检查并按地址写记录 | 0.376 | 2.374 | 2.667 |
| 跳过引擎的逐粒子分发，直接循环 | 0.407 | 2.824 | 3.107 |

- 96,000 粒子下，单独关闭逐粒子视锥检查三轮分别节省 0.500、0.487 和 0.452 ms/帧，是这轮最稳定的单项收益。该差值对应全部可见时省掉的逐粒子检查。
- 保留视锥检查时，按地址写入节省 0.145–0.811 ms/帧。关闭视锥检查后，按地址写入仍三轮都有收益，节省 0.178–0.510 ms/帧。两个改动一起使 96,000 粒子的 CPU 准备加提交从 3.504 降到 2.667 ms/帧，降幅约 24%。
- 直接循环应与同样关闭视锥检查的路径相比。96,000 粒子时三轮的准备耗时变化分别为增加 0.230、减少 0.019 和增加 0.189 ms/帧。这个实验没有发现重写循环本身的稳定收益。

## LOOKAT 朝向的 CPU 和 GPU 求轴

Forge 1.20.1、Oculus 1.7.0、BSL v8.4.01.2 受控配置，RTX 4060 Laptop，1280×720，无帧率上限。每批固定数量和位置，只使用一种朝向。两条 compute 共用 80 B 输入记录，同一内核写出 `PARTICLE` 顶点。CPU 求轴路径调用现有 `applyFacingMode()`，GPU 求轴路径读取最新 tick 的相机相对位置与速度。粒子的自旋和方向组速度由同一个种子生成。

默认背面剔除下，4,096 粒子组把求轴移至 GPU 后，三轮配对的 CPU 耗时分别省了 0.326–0.356 ms/帧（XYZ）、0.374–0.387 ms/帧（Y）和 0.596–0.621 ms/帧（DIRECTION）。空场景对照显示，1.20.1 当前 CPU 绕序使本场景的 `LOOKAT_XYZ`、`LOOKAT_Y` 被背面剔除。后续的画面和性能对照在测试批次关闭背面剔除，结束后恢复。

| 朝向 | Embeddium CPU | CPU 求轴＋compute CPU | GPU 求轴＋compute CPU | GPU 批次 P50 | 整帧 P95 |
